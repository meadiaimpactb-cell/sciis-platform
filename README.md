# منصة المجلس السعودي للمستثمرين الاجتماعيين (SCIIS)

> **Saudi Council for Impact Investors — Platform**
> منصة رقمية تربط المستثمرين الاجتماعيين المعتمدين بفرص المشاريع الاجتماعية المؤهّلة، عبر مسار واضح: تسجيل → عضوية → فرص → اهتمام بموافقة مزدوجة → ربط → متابعة أثر.
> مبنية وفق «الوثيقة التطويرية والتقنية 3.0 — الإصدار البرمجي» (19 أكتوبر 2026، تبني على الإصدار 2.0 دون حذف) والمواصفة الهندسية الملزمة [`docs/SPEC.md`](docs/SPEC.md).

## 1. ما هي المنصة؟

المنصة هي البنية التشغيلية للمجلس. تُنفّذ عشر رحلات مستخدم من الوثيقة الأصلية:

| # | الرحلة | الفاعل | أكواد المتطلبات |
|---|---|---|---|
| 1 | التسجيل والتحقق من البريد والجوال | الجميع | ACC-01..02 |
| 2 | الملف الاستثماري وطلب العضوية واعتمادها | المستثمر / مسؤول العضوية | ACC-03, ACC-06..07, INV-01 |
| 3 | إنشاء ملف الفرصة وتقديمه بقائمة اكتمال | صاحب المشروع | ENT-01..03, ENT-09 |
| 4 | الفرز الأولي وطلب الاستكمال وفق SLA | المراجع | ADM-01..04 |
| 5 | التقييم بمقيّمَين مستقلّين وقرار الأهلية | المقيّمون / المشرف | EVL-01..03 |
| 6 | الملخص التعريفي والترشيح الشفّاف | مسؤول الربط | MAT-01..05 |
| 7 | إبداء الاهتمام والموافقة المزدوجة والملف الكامل | المستثمر / صاحب المشروع | INV-02..04, ENT-06, OPP-01..06 |
| 8 | طلبات المعلومات دون كشف الهوية | الجميع عبر المجلس | OPP-05, MSG-01..02 |
| 9 | الاجتماعات والمحاضر | مسؤول الربط | MTG-01..02 |
| 10 | التقارير والتدقيق وحقوق البيانات | الإدارة / مستعرض التقارير | RPT-01..02, AUD-01..03, PRV-01..05 |

المبدأ الحاكم لكل الرحلات: **الكشف التدريجي (Progressive disclosure)** — لا يرى أي طرف إلا ما يخوّله مستوى وصوله (`visitor → registered → approved_member → granted → connected`) ومستوى حساسية الحقل (ع / د / س / ح). انظر [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) §5.

## 2. المنظومة التقنية ولماذا

### 2.1 القرار الحاسم: لا WordPress ولا Elementor

الوثيقة الأصلية افترضت WordPress + Elementor. **أُزيل هذا الافتراض كليًا** من المنصة للأسباب التالية:

| المشكلة مع WordPress/Elementor | أثرها على المجلس |
|---|---|
| نموذج أمان قائم على إضافات (plugins) من أطراف ثالثة وقاعدة بيانات مشتركة | يتعارض مع مستويات الحساسية الأربعة وسجل التدقيق غير القابل للتعديل (AUD-02) ومتطلبات NCA ECC |
| لا آلة حالات حقيقية ولا صلاحيات على مستوى السجل | مسار الفرصة (12 حالة) والموافقة المزدوجة يتطلبان منطقًا تطبيقيًا لا «حقولًا مخصصة» |
| لا واجهة API موجّهة للجوال من الأصل | تطبيق الجوال (المرحلة الثانية) يحتاج JSON موحّدًا ورموز Bearer وتسجيل أجهزة الدفع |
| منشئ الصفحات يُنتج HTML ثقيلًا وغير محكوم | تجربة RTL وAA للتباين وأداء على الجوال يصعب ضمانها |
| التحديثات التلقائية للإضافات تغيّر السلوك دون اختبار | يخالف بوابة اختبار الاختراق والبيئات المنفصلة (SEC-03/04) |

### 2.2 Laravel ≠ WordPress

كلاهما PHP، لكن الشبه يتوقف عند اللغة:

| البعد | WordPress | Laravel (كما نستخدمه) |
|---|---|---|
| ماهيته | نظام إدارة محتوى مع إضافات وقوالب | إطار تطبيقات: نماذج، سياسات صلاحيات، طوابير، أحداث، اختبارات |
| الواجهة | Themes + منشئ صفحات | **لا واجهة PHP إطلاقًا** (API-only، بلا Blade) — الواجهة Nuxt منفصلة |
| قاعدة البيانات | مخطط ثابت مشترك `wp_*` | مخطط نصمّمه نحن (PostgreSQL، JSONB، قيود صفية، محفّز عدم التعديل للتدقيق) |
| الصلاحيات | أدوار عامة | spatie/laravel-permission + Policies على مستوى السجل (المقيّم يرى ما أُسند له فقط) |
| التوسّع | إضافات من السوق | كود مملوك للمجلس، مختبر بـ Pest، مُنسَّق بـ Pint |

### 2.3 الطبقات

| الطبقة | الاختيار | لماذا |
|---|---|---|
| **الـ API** | PHP 8.3 · Laravel 12 (API-only) | Sanctum (كوكي للويب + Bearer للجوال)، Policies/Gates، Horizon، Notifications (بريد/SMS/داخلية)، Scheduler لتذكيرات SLA، Pest/Pint. الفريق يبني أصلًا بـ Laravel + Vue |
| **قاعدة البيانات** | PostgreSQL 16 | أنواع صارمة، JSONB لإجابات النماذج المرنة، فهارس جزئية، نسخ احتياطي ناضج |
| **الذاكرة والطوابير** | Redis 7 | الطوابير (إشعارات، فحص مستندات، تصدير)، تحديد المعدل، الجلسات |
| **التخزين** | S3-compatible (MinIO محليًا؛ حاوية داخل المملكة إنتاجيًا) | تشفير عند السكون، روابط موقّعة مؤقتة، إصدارات |
| **الويب** | Nuxt 3 (Vue 3 + TS) · Tailwind · Pinia · @nuxtjs/i18n | SSR/prerender للموقع العام (SEO) وبوابة client-only؛ RTL افتراضيًا |
| **الجوال** | Flutter 3 (Dart) | كود واحد لـ iOS/Android، RTL أصيل، يستهلك نفس `/api/v1`؛ **لا WebView** |
| **المدفوعات** | تجريد بوابة + مشغّل Moyasar خلف `FEATURE_PAYMENTS=false` | رسوم العضوية/الخدمات/التدريب/الرعاية فقط — **لا أموال صفقات ولا ضمان** |
| **المصادقة** | Sanctum + TOTP (إلزامي للفريق) + OTP بريد وجوال | ACC-01, ACC-05 |
| **المراقبة** | سجلات JSON، `/health`، Horizon، خطاف Sentry | BKP-03 |

## 4. البدء السريع (Docker)

**المتطلبات:** Docker 24+ مع Compose v2، `make`، 8 GB ذاكرة متاحة.

```bash
git clone <repo-url> sciis-platform && cd sciis-platform
make env            # ينشئ .env من .env.example — عدّل كلمات مرور DB وMinIO
make up             # يبني ويشغّل كل الخدمات
make key            # يولّد APP_KEY
make fresh          # يُنشئ المخطط ويزرع بيانات افتراضية (كلها مُعلَّمة "(افتراضي)")
```

| الخدمة | العنوان |
|---|---|
| API health | <http://localhost:8000/api/v1/health> |
| الموقع والبوابة | <http://localhost:3000> |
| Mailpit (البريد الصادر) | <http://localhost:8025> |
| MinIO console | <http://localhost:9001> |
| Horizon | <http://localhost:8000/horizon> (حساب staff) |
| مرجع الـ API التفاعلي | `make openapi-preview` → <http://localhost:8081> |

حسابات البيانات الافتراضية (SPEC §11): 3 مستثمرون، 3 أصحاب مشاريع، الطاقم الكامل، 8 فرص. كلمات المرور في `api/database/seeders/README.md`.

### أوامر يومية

```bash
make logs s=api        # متابعة سجلات خدمة
make test              # Pest + Vitest/typecheck
make lint              # Pint + composer audit + ESLint + npm audit + Redocly
make shell-api         # داخل حاوية الـ API
make backup            # نسخة pg_dump مشفّرة (BACKUP_PASSPHRASE مطلوب)
```

## 5. البيئات

| البيئة | الغرض | البيانات | الفروع | ملاحظات |
|---|---|---|---|---|
| **local** | تطوير على Docker | افتراضية فقط | أي فرع | `APP_DEBUG=true`، Mailpit، MinIO |
| **test** | اختبار القبول (UAT) + اختبار الاختراق | افتراضية فقط | `develop` | نفس طوبولوجيا الإنتاج، SMS على مزوّد اختباري |
| **production** | التشغيل | حقيقية | `main` بوسم إصدار | داخل المملكة، نسخ احتياطي ليلي، 2FA إلزامي للفريق |

الفصل بين البيئات (SEC-04): ملف `.env` مستقل لكل بيئة، **لا تُنسخ بيانات إنتاجية إلى أي بيئة أخرى أبدًا**؛ البذور تُنتج بيانات تركيبية فقط. التفاصيل في [`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md).

## 7. قرارات مفتوحة (من الوثيقة)

| القرار | الحالة | أين يُضبط |
|---|---|---|
| سياسة وصول المستثمرين للفرص (`nomination_only` / `browse_all` / `both`) | **معلّق** بانتظار الرأي القانوني — الافتراضي `nomination_only` | `settings: opportunity.access_policy` |
| الاسم المختصر (SCII / SCIIS) | معلّق | `settings: platform.short_name` |
| إقرار المستثمر المؤهَّل | يُحفظ ولا يُعرض | `investor_profiles.accredited_declaration` |
| النصوص القانونية (الخصوصية، الشروط، NDA) | نماذج أولية «بانتظار الاعتماد القانوني» | `pages` + إصدارات في `consents` |
| بوابة الدفع | معطّلة في P1 | `FEATURE_PAYMENTS` |

## 9. المساهمة

1. فرع من `develop` باسم `feat/<code>-<slug>` (مثال: `feat/ENT-06-owner-decision`).
2. كل تغيير يذكر كود المتطلب في رسالة الـ commit وفي تعليق الكود والاختبار.
3. `make lint && make test` قبل فتح PR؛ CI يجب أن يمرّ (الجوال استشاري حتى التفعيل).
4. أي حقل جديد في الـ API: يُضاف أولًا إلى `docs/openapi.yaml` ثم إلى الـ Resource ثم إلى `web/types` و`mobile/lib/core/models`.
5. لا بيانات حقيقية في البذور أو الاختبارات أو لقطات الشاشة.
